The problem: bulk semantic processing

Section 1

Many tasks need models orchestrated over a whole corpus: summarize this week's ArXiv papers, extract diagnoses from patient reports, validate hypotheses from meeting transcripts. The hope is an analytics system that does for this what RDBMSes did for tabular data.

Batched-inference primitives

AI UDFs in database products and several research systems apply an LLM row by row. They have no ranking, grouping or joining, which need algorithms that compose many model calls.

Best-effort analytics

DocETL and UQE support richer operations but optimize empirically. With no definition of correct behavior, there is no accuracy guarantee.

Two questions follow: how should developers express semantic queries, and how should the engine be built for efficiency and accuracy? The core difficulty is the ambiguity of natural-language instructions and LLM outputs.

What a semantic operator is

Sections 2.1 to 2.3

Definition. A semantic operator is a declarative transformation over one or more datasets, parameterized by a natural language expression (langex). Many AI algorithms can implement it; its correct behavior is defined by a reference algorithm.
  • Model–data independence. Application logic is separated from the AI algorithm that decides which model calls process which records.
  • World model M. Semantics are defined against a model, in practice the strongest LLM available. E.g. filter returns {ti ∈ T : lM(ti) = 1}.
  • Reference algorithm. A tractable, high-quality algorithm. Its LLM-call cost is often linear or quadratic in data size.
Correct optimization. An alternative algorithm that reduces cost while meeting an accuracy target γ, relative to the reference algorithm, with probability 1 − δ. This borrows from approximate query processing.

An example program

Figure 1: a paper digest in three operator calls

def paper_digest(research_interest, baseline):
    return papers_df \
      .sem_search(abstracts, research_interest, K=100) \
      .sem_filter(f"the paper {{abstracts}} claim to outperform {baseline}") \
      .sem_agg(f"Write a digest summarizing {{abstracts}} and their relevance to {research_interest}")
sem_search (top-k by similarity)→sem_filter (natural-language predicate)→sem_agg (summary)

The programmer writes what is wanted. A naive filter would call the LLM once per record; the engine may instead use a lightweight model or vector index for some records and reserve the LLM for the rest, transparently and with guarantees.

Semantic aggregation

Section 2.4 (reference algorithm only; optimization is not studied in this paper)

  • Langex is a commutative, associative aggregation, applicable to any subset of rows. Finite context is an implementation detail.
  • Fold: a linear pass, acci = M({acci−1, ti}, l). Sequential.
  • Hierarchical reduce (chosen): combine n inputs per round until one answer remains. Prior work found higher quality for summarization, and it parallelizes.
  • Input order inside a prompt can affect quality, so LOTUS exposes a partitioner function to override commutativity.

Why filter and join are expensive

Reference algorithms, Section 2.4

Semantic filter

One batched LLM call per tuple: the predicate plus an instruction to emit a boolean. Rows are processed independently, avoiding long-context failures such as "lost in the middle". Cost: O(|T|) calls.

Semantic join

Nested loop: one predicate call per pair in T1 × T2. Cost: O(|T1|·|T2|) calls.

Goal for both: meet recall target γR and precision target γP, relative to the reference output, with probability 1 − δ, while calling the oracle LLM as little as possible.

The proxy may be poor on some tasks or records. The algorithm therefore measures proxy quality at query time by sampling and comparing to the oracle, and defers to the oracle when the proxy cannot be trusted.

Optimizing semantic filter: a guaranteed cascade

Section 3.1, Algorithm 1: thresholds learned on a cheap proxy, checked against the oracle

  • Proxy score: a small LLM (Llama-8B) predicts the predicate. The score is the log-probability of the True or False token, binned into q = 50 quantiles.
  • Sampling: importance sampling (weights from √ proxy score, following Kang et al.) mixed with a uniform sample. Default size: the larger of 1% of the data and 100; evaluation uses 0.01% with a floor of 100.
  • Thresholds: the central limit theorem gives τ⁺ (precision) and τ⁻ (recall), each at δ/2, with a correction for multiple hypothesis tests. Then set τ⁺ to max(τ⁺, τ⁻).
  • Versus earlier cascades: this targets filters only, so light scoring suffices. Without log-probabilities, other uncertainty estimates would be needed.

Optimizing semantic join

Section 3.2: same guarantee form, but the proxy must be far cheaper than an LLM over n² pairs

  • sim-filter uses embedding similarity between join keys. It works when matching pairs tend to look alike, which is not always true.
  • project-sim-filter asks the LLM, once per left row and fully in parallel, what the matching right key would be, without seeing the right table. It helps when true matches have low raw similarity.
  • Example (Figure 2): join papers to datasets with "the paper {abstract} uses the {dataset_name}". The projection asks which dataset each abstract uses.

Semantic top-k

Reference algorithm (Section 2.4) and a lossless optimization (Section 3.4)

Reference design

  • Comparisons: pairwise prompts (two tuples in, one label out). Pointwise and listwise rankers suffer calibration and long-context failures.
  • Aggregation: quick-select. Each round picks a pivot and compares every remaining tuple to it, so a round is fully parallel.

Optimization: embedding pivot

  • If the ranking correlates with embedding similarity to the query, use the (k+ε)-th item of the embedding order as the first pivot.
  • No accuracy loss. With no correlation this reduces to a random pivot; an adversarial pivot costs one extra round.

Semantic group-by

Sections 2.4 and 3.3: a two-stage clustering heuristic, with a proxy for stage-2 assignment

Objective: choose C labels that maximize the summed best label score over tuples. This is NP-hard clustering, so the reference algorithm uses a heuristic.

  • Stage 1 (reference): the LLM proposes a candidate label per tuple. Labels are embedded and clustered with k-means, and each cluster's top-k tuples are summarized with sem_agg.
  • Stage 2 (optimized): similarity between a tuple's candidate label and each center is the proxy. Above τ the center is used directly; otherwise the oracle labels the tuple.
  • Threshold search reuses the filter's procedure, with classification accuracy over the C groups as the metric. Sampling takes under 5 s.
  • Topic analysis (647 ArXiv papers, C = 5): labels such as recommendation, retrieval, LLM applications, AI security and robotics emerge in 44 s.
  • Tradeoff (Fig. 6): the proxy alone is 17.4× faster than the oracle but about 39% less accurate. The accuracy target interpolates between the two.

The LOTUS system

Section 4: LLMs Over Tables of Unstructured and Structured data

Architecture

  • Extends Pandas with a DataFrame API; the same semantics could sit behind SQL.
  • vLLM for batched inference; FAISS for local, on-disk vector indices.
  • Structured and unstructured fields (text, images) can both appear in a langex.
  • sem_index builds a semantic index; load_sem_index reloads it.

Beyond the core operators

  • sem_sim_join: match by embedding similarity, like an equi-join, enabling vector search.
  • sem_search: top-k by similarity, with optional n_rerank re-ranking.
  • sem_extract: project to verbatim sub-strings, useful for entities and quotes.
  • Every operator takes an optional accuracy target and error probability.
papers_df.sem_join(dataset_df, "The paper {abstract:left} uses the {dataset_name:right}.")
papers_df.sem_topk("The paper has the funniest {title}", K=5)
papers_df.sem_group_by("What is the main research topic of the paper {abstract}", C=10)

The accuracy, latency and cost tradeoff is task-specific, so benchmark several targets and choose an operating point.

Do the guarantees hold?

Section 5.5: sem_filter on FEVER, Llama-70B oracle, Llama-8B and TinyLlama-1B proxies, δ = 0.2 and 0.4

  • Calibration: observed average recall and precision (over 20 trials) rise with the configured targets, for both proxies.
  • Proxy quality: the weaker TinyLlama needs more oracle calls at the same target.
  • Cost curve: oracle calls do not grow linearly with the target; the extra cost of a gain depends on where in the range it falls.
  • Failure rate: with γR = γP = 0.9 and TinyLlama over 50 trials, the observed failure rate stayed below the configured δ, as expected from a conservative implementation.
Scope of the guarantee. It holds for individual operators relative to the reference algorithm, not against ground truth. If the reference is poor on a task, the guarantee inherits that.

Limitations and discussion

Section 7

  • No end-to-end guarantee. Each operator has its own guarantee. A future query could split one global error budget across operators.
  • Narrow plan search. Optimizations are simple, cost-based rules. Searching richer plans (cheaper models, vector or traditional indexes, code generation) is open.
  • No equivalence rules yet for plan rewrites such as operator reordering.
  • Reference algorithms are strong but not known to be optimal. Aggregation optimization is deferred to an extended version.

Questions for the seminar

  • What does a guarantee relative to an LLM-defined reference mean if the reference is wrong?
  • How would errors compose across a filter → join → aggregation pipeline?
  • When does embedding similarity fail as a proxy, and how could the optimizer detect that cheaply?
