🤔What a semantic operator is

Sections 2.1 to 2.3

Definition. A semantic operator is a declarative transformation over one or more datasets, parameterized by a natural language expression (langex). Many AI algorithms can implement it; its correct behavior is defined by a reference algorithm.
Correct optimization. A cheaper alternative algorithm is valid if it meets an accuracy target γ relative to the reference algorithm, with confidence probability 1 − δ (adapted from approximate query processing).

An example program: 3 lines instead of 200+

Figure 1: sem_search, sem_filter, and sem_agg are built-in LOTUS methods—you supply the natural-language criteria

Before: manual LLM script

  • About 200+ lines of prompt templates, batching loops and retry logic.
  • Vector index and glue code to connect search results to LLM calls.
  • Every row goes to the LLM, so cost scales with the whole corpus.
  • Threshold picked by hand; accuracy is unverified.

After: LOTUS built-in operators (3 lines)

  • No need to implement the operators—call LOTUS methods like DataFrame functions and pass your natural-language instructions.
  • The engine routes easy rows to a cheap proxy and hard rows to the oracle LLM.
  • Each operator supports accuracy targets with a statistical guarantee against the reference.
def paper_digest(research_interest, baseline):
    return papers_df \
      .sem_search(abstracts, research_interest, K=100) \
      .sem_filter(f"the paper {{abstracts}} claim to outperform {baseline}") \
      .sem_agg(f"Write a digest summarizing {{abstracts}} and their relevance to {research_interest}")
sem_search (top-k by similarity)→sem_filter (natural-language predicate)→sem_agg (summary)

Operators are provided by LOTUS; the developer writes what is wanted, while the engine decides how to execute and optimize it.

Relaxations & Guarantees

All operators accept optional accuracy targets (γ, δ). Total ordering in sem_topk / sem_group_by can soften to partial orders with noisy LLM comparisons.

Semantic aggregation

Section 2.4 (reference algorithm only; optimization is not studied in this paper)

  • Langex is a commutative, associative aggregation over subsets of tuples; finite context window is an implementation detail.
  • Fold (sequential): updates state one tuple at a time via acci = M({acci−1, ti}, l) over i = 1..|T| (|T| sequential steps).
  • Hierarchical reduce (chosen): partitions inputs into groups of size n per round, computes partial results in parallel, and repeats for ⌈logn |T|⌉ rounds until one output remains.
  • Prompt order can still affect outputs in practice, so LOTUS provides a partitioner hook to override commutativity when needed.

Why filter and join are expensive

Reference algorithms (Section 2.4) and optimization targets

Semantic filter · cost O(|T|)

One batched LLM call per tuple (predicate + boolean rule). Rows run independently to avoid "lost in the middle" context errors.

Table size |T|Max LLM calls
1,000 rows1,000
100,000 rows100,000

Semantic join · cost O(|T1|·|T2|)

Nested loop over T1 × T2: one call per pair. Cost grows quadratically as either table gets bigger.

|T1| × |T2|Max LLM calls
1,000 × 1,0001,000,000
10,000 × 10,000100,000,000
Optimization goal: Cut calls to the expensive oracle LLM while meeting targets relative to the reference output with probability ≥ 1 − δ:
  • Recall target (γR): share of reference-true items kept by the plan.
  • Precision target (γP): share of plan-kept items that are also reference-true.
Why check proxy at query time? Cheap proxies (small LLMs or embedding similarity) can be noisy on some data. LOTUS estimates proxy quality at query time via sampling against the oracle and sends uncertain items to the oracle to keep the (γR, γP, 1 − δ) guarantee.

Optimizing semantic filter: a guaranteed cascade

Section 3.1, Algorithm 1: cheap proxy scores + statistical thresholds + oracle fallback

ComponentHow it works & key math
Proxy scoreSmall LLM (e.g., Llama-8B) outputs log-prob of True/False token, split into q = 50 quantile bins.
SamplingImportance sampling (weight ∝ √ proxy score, Kang et al.) + uniform sample. Default: max(1% of rows, 100); eval: 0.01% (min 100).
Cutoffs (τ⁻, τ⁺)Central limit theorem + normal approx. + multiple-test correction, split error budget δ/2 each; enforce τ⁺ ← max(τ⁺, τ⁻).
Why lighter?Built specifically for boolean filters, so token log-prob is enough without heavy uncertainty models.

Semantic top-k

Reference algorithm (Section 2.4) and a lossless optimization (Section 3.4)

Reference design

  • Comparisons: pairwise prompts (two tuples in, one label out). Pointwise and listwise rankers suffer calibration and long-context failures.
  • Aggregation: quick-select. Each round picks a pivot and compares every remaining tuple to it, so a round is fully parallel.

Optimization: embedding pivot

  • If the ranking correlates with embedding similarity to the query, use the (k+ε)-th item of the embedding order as the first pivot.
  • No accuracy loss. With no correlation this reduces to a random pivot; an adversarial pivot costs one extra round.

  • Quick-select runs 16–32% faster than heap despite sometimes making more calls, because heap updates force sequential calls.
  • Embedding pivot cut SciFact latency by about 10% at equal quality, where rank correlates with similarity.

Semantic group-by

Sections 2.4 and 3.3: two-stage clustering heuristic with threshold-based proxy assignment

Goal: pick C group labels to maximize the total best-label score across tuples ti. Exact clustering is NP-hard, so LOTUS uses a two-stage heuristic.

AspectFormula / RuleIntuition & Trade-off
GuaranteeP(Acc_proxy ≥ γ) ≥ 1 − δMatches reference group labels at least γ with confidence 1 − δ; tuning γ slides between speed and accuracy.
SamplingUniform sample (< 5 s)Gives every one of the C clusters a fair chance when estimating τ (unlike single-class filter/join importance sampling).
ArXiv (N=647, C=5)17.4× speedup vs. ~39% acc drop (proxy only)Discovers 5 topic labels in 44 s; setting a target γ lets the engine call the oracle only when similarity falls below τ.

🪷The LOTUS system

Section 4: Declarative semantic operators over structured + unstructured tables

Extended operators

  • sem_sim_join: embedding similarity match (like equi-join + vector search).
  • sem_search: similarity top-k with optional n_rerank re-ranking.
  • sem_extract: pulls exact text spans (entities or quotes).

Practical usage

  • Build/reload indexes via sem_index and load_sem_index.
  • Tune γ and δ per task because cost–accuracy curves vary by workload.
papers_df.sem_join(dataset_df, "The paper {abstract:left} uses the {dataset_name:right}.")
papers_df.sem_topk("The paper has the funniest {title}", K=5)
papers_df.sem_group_by("What is the main research topic of the paper {abstract}", C=10)

Scope of the guarantee: Holds per operator relative to the reference algorithm (prob. ≥ 1 − δ), not against ground truth. If the reference is wrong on a task, the guarantee still measures agreement with that reference.

Math check (for DB discussion)

Each LOTUS operator enforces P(acc ≥ γ) ≥ 1 − δ relative to the reference algorithm. Across m independent stages with budgets δ₁, …, δₘ, union bound gives max total failure risk ≤ ∑ δᵢ (not yet unified into one end-to-end optimizer).

Real-world adoption

Ideas from classic ML cascades (e.g., BlazeIt / SUPG) adapt to LLM scoring, and Google added experimental semantic operators to BigQuery DataFrames after the preprint.

Limitations and discussion

Section 7

  • No end-to-end guarantee. Each operator has its own guarantee. A future query could split one global error budget across operators.
  • Narrow plan search. Optimizations are simple, cost-based rules. Searching richer plans (cheaper models, vector or traditional indexes, code generation) is open.
  • No equivalence rules yet for plan rewrites such as operator reordering.
  • Reference algorithms are strong but not known to be optimal. Aggregation optimization is deferred to an extended version.

Questions for the seminar

  • What does a guarantee relative to an LLM-defined reference mean if the reference is wrong?
  • How would errors compose across a filter → join → aggregation pipeline?
  • When does embedding similarity fail as a proxy, and how could the optimizer detect that cheaply?
